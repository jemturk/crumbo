# Known Bugs

Audit of `src/` and the `incoming-call` native module, current as of 2026-07-16.

## Critical

1. **The entire family database is readable and writable by anyone with the app.** All parent data — including the **plaintext parent password**, kids' names, cookie codes, and friend lists — is stored as a JSON blob in the `profiles.push_token` column (`storage.ts:427-441`). Login, pairing, and kid-login all work by the client querying *other families' rows* with `.like()` scans (`storage.ts:630-685`), which only works if the table is fully readable by the anon key baked into the APK. Anyone can dump every family's password, impersonate any parent (auth is a client-side string compare at `gate.tsx:102`), read any two kids' chat history (`storage.ts:216-240` takes arbitrary code pairs), and write messages as anyone. This needs real auth (Supabase Auth + RLS) rather than app-side fixes.

2. ~~**Cookie codes can collide across families.** `createKidProfile` picks `CRUM-XXX-XXX` randomly — only 810,000 combinations — with no uniqueness check against the server (`storage.ts:90-94`). Two kids in different families getting the same code cross-wires everything keyed on it: messages, calls, pairing, and kid login (~50% chance of at least one collision by ~1,000 kids).~~ **Fixed (app-level; the real fix is the schema rework tracked under #1).** `createKidProfile` now checks the server for an existing kid with the candidate code and retries on a real collision (`generateUniqueCookieCode`). Codes still live nested in each parent row's JSON blob rather than their own indexed column, so this can't fully close the race the way a DB unique constraint would — it converts "guaranteed to collide eventually, unchecked" into "requires two devices generating the same code in the same instant."

3. ~~**A parent's locks don't actually stop calls.** The `callingDisabled`/`videoCallingDisabled` locks only hide the *outgoing* call buttons. An incoming call signal is handled with no lock check at all (`use-call.ts:314-338`) — a kid whose calling was disabled still receives, sees, and can accept calls. Locks are also only refreshed when the kid visits the friends-list screen (`chat/index.tsx:69`); a kid sitting inside an open chat keeps chatting/calling indefinitely after the parent flips the lock.~~ **Fixed.** An incoming `START_*_CALL` signal is now checked against the lock before anything is shown — both in `use-call.ts` (foreground/JS-alive path, which auto-declines and logs a missed call) and in `callkeep.ts`'s background push task (killed/backgrounded path, using the locally cached profile). `chat/[friendId].tsx` also now re-syncs the kid's profile (not just the local cache) on load and polls every `LOCK_REFRESH_INTERVAL_MS` (20s) while the screen stays focused, so a lock flipped mid-conversation takes effect without navigating away and back.

## High

4. ~~**Messages sent offline are silently lost.** `sendMessage` writes locally and swallows a failed Supabase insert (`storage.ts:256-274`); the next `getMessages` then *overwrites* the local cache with server state (`storage.ts:202-204`), deleting the message everywhere with no error shown. There's no outbox/retry.~~ **Fixed.** Added a per-friend outbox (`crumbo_outbox_<friendId>`): `sendMessage`/`sendCallLogMessage` queue an entry there when the Supabase insert fails, and `getMessages` retries the outbox before its server-sync overwrite, merging in whatever is still unsynced instead of discarding it.

5. ~~**One unanswered call produces duplicate "Missed Call" entries.** Both sides run their own 45-second ring timer started within ~1s of each other (`use-call.ts:552-566`); when a call times out, both timers fire before the other side's END/CANCEL signal lands, so *both* write a missed-call row to the shared table, and both devices display both. The writes should be deduplicated per `callUUID` (e.g., include it in the log row and dedupe on render or insert).~~ **Fixed.** `use-call.ts` now embeds `callUUID` in every `[CALL_LOG:...]` row it writes; `storage.ts`'s `dedupeCallLogs` collapses rows sharing a `callUUID` down to one (deterministic tiebreak on `id`) in `getMessages`, the realtime subscriber, and `sendCallLogMessage`.

6. ~~**Cancelling the subscription doesn't affect the kid's device.** The dashboard promises "Your child won't be able to chat anymore" (`dashboard.tsx:228`), but it only sets a local flag on the *parent's* device; nothing propagates to a kid device, which checks only its own local flag (`chat/index.tsx:61-67`).~~ **Fixed.** `handleCancelSubscription` now pushes the cancellation to Supabase via `syncParentData()` (rolling back the local flag if that fails), and `syncKidProfileAndFriends` mirrors the parent's actual `subscribed` state onto the kid's device; `chat/index.tsx` now runs that sync *before* its `isSubscribed()` gate so a cancellation is caught on the very next focus.

## Medium

7. ~~**QR scanner fires the pairing flow multiple times.** `onBarcodeScanned` fires every frame, and the `if (!qrScannerVisible) return` guard reads a stale closure value (`dashboard.tsx:1016-1018`), so several events pass before the re-render — duplicate `pairKidsViaQRCode` calls and stacked alerts. Standard fix is a `useRef` scanned-once latch.~~ **Fixed.** Added a `qrScanHandledRef` latch, checked/set synchronously in `onBarcodeScanned` and reset when the scanner (re)opens — reading a ref instead of the stale `qrScannerVisible` closure value actually stops duplicate frames.

8. ~~**Kid logout breaks the parent's state on a shared device.** `logoutKid` removes `IS_SUBSCRIBED` (`storage.ts:687-691`), which is the same flag the parent dashboard uses — after a kid logs out, the parent area shows "not subscribed."~~ **Fixed.** `logoutKid()` now only clears `IS_SUBSCRIBED` when there's no parent email registered locally on the device — a shared device with a parent account keeps its subscription flag intact across a kid logout.

9. ~~**Kids' names and codes are sent to a third-party server.** The pairing QR is generated by fetching `api.qrserver.com` with the kid's name and cookie code in the URL (`dashboard.tsx:983`) — contradicting the home screen's "No child data will ever be collected" promise, and it needs network. `react-native-qrcode-svg` renders locally.~~ **Fixed.** Installed `react-native-qrcode-svg`; the pairing QR is now rendered locally, no network call or third party involved.

10. ~~**Any network error marks friends "pending" and locks the chat.** `checkFriendPairingStatus` returns `'pending'` on failure (`storage.ts:805-807`), so an offline kid sees all friends demoted to "Waiting for parent approval" with the input disabled. It also runs one sequential Supabase query per friend on every dashboard focus.~~ **Fixed.** `checkFriendPairingStatus` now throws on a query/network failure instead of returning `'pending'`; both callers catch that and keep the friend's last known status instead of demoting them. The per-friend checks in `chat/index.tsx` also now run concurrently (`Promise.all`) instead of one at a time.

11. ~~**Concurrent writes can drop messages locally.** `sendMessage`, `sendCallLogMessage`, and the realtime subscriber all read-modify-write the same AsyncStorage key with no serialization (`storage.ts:242-292`, `storage.ts:377-382`) — a send racing an incoming message loses one of them until the next server sync.~~ **Fixed.** Added a per-`friendId` promise queue (`withMessagesLock`) that all five read-modify-write sites on the messages cache (`getMessages`'s server-sync overwrite, `sendMessage`, `sendCallLogMessage`, `receiveMockMessage`, and the realtime subscriber) now go through, so they run one at a time per friend instead of racing.

12. ~~**IDs are `Math.random()` 7-char strings** for messages, friends, and call logs (`storage.ts:244`) — a global-table collision makes the insert fail silently, and combined with #4 the message then evaporates. Use `crypto.randomUUID()`-style IDs.~~ **Fixed.** Installed `expo-crypto`; all message, friend, and call-log IDs in `storage.ts` now use `Crypto.randomUUID()`.

## Low

13. ~~**Ring-forever edge case:** if the caller's CANCEL push fails (failure is swallowed at `callSignaling.ts:137-140`) and the callee's app is killed, the `FLAG_INSISTENT` CallStyle notification rings until manually dismissed — nothing local ever times it out.~~ **Fixed.** `IncomingCallModule` now schedules an `AlarmManager` backstop alongside every notification (`scheduleRingTimeout`, matching JS's 45s `RING_TIMEOUT_MS`) that silences the ring/Telecom connection and notifies JS (`onMissFromNotification`) even if the process was killed; whichever of answer/decline/timeout fires first cancels the other two.
14. ~~**Agora UID collisions:** `hashCode(cookieCode)` maps to 32 bits (`agora.ts:11-20`); two colliding participants in one call would kick each other. Astronomically rare with 2 parties, but silent if it happens.~~ **Fixed.** Added `resolveCallUid()` (`agora.ts`), which both sides compute from *both* participants' codes and deterministically tie-breaks (lexicographic order) if their hashes collide, so a collision can no longer produce the same UID for both callers.
15. ~~**Registration race:** two devices registering the same email concurrently both pass the exists-check and the second upsert silently overwrites the first (`gate.tsx:148-176`).~~ **Fixed.** Added `StorageService.createParentAccount()`, a real `INSERT` (not upsert) backed by a new unique index on `profiles.cookie_code` (`supabase/migrations/20260731000000_profiles_cookie_code_unique.sql` — **needs to be applied to the live database**); the loser now gets a unique-violation and its local credentials are rolled back instead of silently overwriting the winner's row.
16. ~~**Deprecated `Clipboard` from `react-native`** (`dashboard.tsx:12`) — removed in newer RN; should move to `expo-clipboard`.~~ **Fixed.** Installed `expo-clipboard`; `dashboard.tsx` now uses `Clipboard.setStringAsync`.
17. ~~**Behavioral quirk:** pressing back (or any unmount) during an incoming ring silently *declines* the call (`use-call.ts:568-581`), so the caller gets "busy" — most apps keep ringing.~~ **Fixed.** Unmounting while an incoming call is still ringing no longer sends `DECLINE_CALL`; the ring is left alone (native notification/CallKeep own it independently), matching normal phone behavior. Connected/outgoing-ringing calls still hang up on unmount as before.

## High (found 2026-08-06)

18. **The `verify-email` and `reset-password-web` web fallback pages don't actually work.** These two Supabase Edge Functions (`supabase/functions/verify-email`, `supabase/functions/reset-password-web`) exist to give a real confirmation/reset screen to anyone who opens a Crumbo account-recovery email on a device without the app installed — see their own header comments. Two compounding causes:
    - (a) `supabase/config.toml`'s `additional_redirect_urls` never listed either function's URL, so `resetPasswordForEmail`/signup's `redirectTo` was silently ignored by Supabase Auth, which fell back to `site_url` (`crumbo://`) instead — the browser tried to open the nonexistent app directly, never reaching either page at all. **Fixed** by adding both function URLs to the live project's Redirect URLs allow-list (Authentication → URL Configuration).
    - (b) Even once reached, Supabase Edge Functions on the shared `*.supabase.co` domain forcibly rewrite any `text/html` GET response to `text/plain` and inject `Content-Security-Policy: default-src 'none'; sandbox` — confirmed via `curl -D-` against both deployed functions. The page renders as raw unstyled source, and for `reset-password-web` specifically — which depends entirely on an inline `<script>` to run the PKCE code exchange and reveal the password form — nothing beyond the static "Verifying your reset link…" text ever appears; password reset is completely non-functional for this whole audience (desktop, or a phone without the app). **Not fixed** — this is a platform restriction on the shared domain, not something fixable in the function code. Needs either: moving both pages to real static hosting (Vercel/Netlify/Cloudflare Pages/GitHub Pages — neither page needs server-side logic; `reset-password-web` just runs `supabase-js` client-side with the public anon key), or Supabase Pro + a custom domain for Edge Functions.
