# Known Bugs

Audit of `src/` and the `incoming-call` native module, current as of 2026-07-16.

## Critical

1. **The entire family database is readable and writable by anyone with the app.** All parent data — including the **plaintext parent password**, kids' names, cookie codes, and friend lists — is stored as a JSON blob in the `profiles.push_token` column (`storage.ts:427-441`). Login, pairing, and kid-login all work by the client querying *other families' rows* with `.like()` scans (`storage.ts:630-685`), which only works if the table is fully readable by the anon key baked into the APK. Anyone can dump every family's password, impersonate any parent (auth is a client-side string compare at `gate.tsx:102`), read any two kids' chat history (`storage.ts:216-240` takes arbitrary code pairs), and write messages as anyone. This needs real auth (Supabase Auth + RLS) rather than app-side fixes.

2. **Cookie codes can collide across families.** `createKidProfile` picks `CRUM-XXX-XXX` randomly — only 810,000 combinations — with no uniqueness check against the server (`storage.ts:90-94`). Two kids in different families getting the same code cross-wires everything keyed on it: messages, calls, pairing, and kid login (~50% chance of at least one collision by ~1,000 kids).

3. **A parent's locks don't actually stop calls.** The `callingDisabled`/`videoCallingDisabled` locks only hide the *outgoing* call buttons. An incoming call signal is handled with no lock check at all (`use-call.ts:314-338`) — a kid whose calling was disabled still receives, sees, and can accept calls. Locks are also only refreshed when the kid visits the friends-list screen (`chat/index.tsx:69`); a kid sitting inside an open chat keeps chatting/calling indefinitely after the parent flips the lock.

## High

4. **Messages sent offline are silently lost.** `sendMessage` writes locally and swallows a failed Supabase insert (`storage.ts:256-274`); the next `getMessages` then *overwrites* the local cache with server state (`storage.ts:202-204`), deleting the message everywhere with no error shown. There's no outbox/retry.

5. **One unanswered call produces duplicate "Missed Call" entries.** Both sides run their own 45-second ring timer started within ~1s of each other (`use-call.ts:552-566`); when a call times out, both timers fire before the other side's END/CANCEL signal lands, so *both* write a missed-call row to the shared table, and both devices display both. The writes should be deduplicated per `callUUID` (e.g., include it in the log row and dedupe on render or insert).

6. **Cancelling the subscription doesn't affect the kid's device.** The dashboard promises "Your child won't be able to chat anymore" (`dashboard.tsx:228`), but it only sets a local flag on the *parent's* device; nothing propagates to a kid device, which checks only its own local flag (`chat/index.tsx:61-67`).

## Medium

7. **QR scanner fires the pairing flow multiple times.** `onBarcodeScanned` fires every frame, and the `if (!qrScannerVisible) return` guard reads a stale closure value (`dashboard.tsx:1016-1018`), so several events pass before the re-render — duplicate `pairKidsViaQRCode` calls and stacked alerts. Standard fix is a `useRef` scanned-once latch.

8. **Kid logout breaks the parent's state on a shared device.** `logoutKid` removes `IS_SUBSCRIBED` (`storage.ts:687-691`), which is the same flag the parent dashboard uses — after a kid logs out, the parent area shows "not subscribed."

9. **Kids' names and codes are sent to a third-party server.** The pairing QR is generated by fetching `api.qrserver.com` with the kid's name and cookie code in the URL (`dashboard.tsx:983`) — contradicting the home screen's "No child data will ever be collected" promise, and it needs network. `react-native-qrcode-svg` renders locally.

10. **Any network error marks friends "pending" and locks the chat.** `checkFriendPairingStatus` returns `'pending'` on failure (`storage.ts:805-807`), so an offline kid sees all friends demoted to "Waiting for parent approval" with the input disabled. It also runs one sequential Supabase query per friend on every dashboard focus.

11. **Concurrent writes can drop messages locally.** `sendMessage`, `sendCallLogMessage`, and the realtime subscriber all read-modify-write the same AsyncStorage key with no serialization (`storage.ts:242-292`, `storage.ts:377-382`) — a send racing an incoming message loses one of them until the next server sync.

12. **IDs are `Math.random()` 7-char strings** for messages, friends, and call logs (`storage.ts:244`) — a global-table collision makes the insert fail silently, and combined with #4 the message then evaporates. Use `crypto.randomUUID()`-style IDs.

## Low

13. ~~**Ring-forever edge case:** if the caller's CANCEL push fails (failure is swallowed at `callSignaling.ts:137-140`) and the callee's app is killed, the `FLAG_INSISTENT` CallStyle notification rings until manually dismissed — nothing local ever times it out.~~ **Fixed.** `IncomingCallModule` now schedules an `AlarmManager` backstop alongside every notification (`scheduleRingTimeout`, matching JS's 45s `RING_TIMEOUT_MS`) that silences the ring/Telecom connection and notifies JS (`onMissFromNotification`) even if the process was killed; whichever of answer/decline/timeout fires first cancels the other two.
14. ~~**Agora UID collisions:** `hashCode(cookieCode)` maps to 32 bits (`agora.ts:11-20`); two colliding participants in one call would kick each other. Astronomically rare with 2 parties, but silent if it happens.~~ **Fixed.** Added `resolveCallUid()` (`agora.ts`), which both sides compute from *both* participants' codes and deterministically tie-breaks (lexicographic order) if their hashes collide, so a collision can no longer produce the same UID for both callers.
15. ~~**Registration race:** two devices registering the same email concurrently both pass the exists-check and the second upsert silently overwrites the first (`gate.tsx:148-176`).~~ **Fixed.** Added `StorageService.createParentAccount()`, a real `INSERT` (not upsert) backed by a new unique index on `profiles.cookie_code` (`supabase/migrations/20260731000000_profiles_cookie_code_unique.sql` — **needs to be applied to the live database**); the loser now gets a unique-violation and its local credentials are rolled back instead of silently overwriting the winner's row.
16. ~~**Deprecated `Clipboard` from `react-native`** (`dashboard.tsx:12`) — removed in newer RN; should move to `expo-clipboard`.~~ **Fixed.** Installed `expo-clipboard`; `dashboard.tsx` now uses `Clipboard.setStringAsync`.
17. ~~**Behavioral quirk:** pressing back (or any unmount) during an incoming ring silently *declines* the call (`use-call.ts:568-581`), so the caller gets "busy" — most apps keep ringing.~~ **Fixed.** Unmounting while an incoming call is still ringing no longer sends `DECLINE_CALL`; the ring is left alone (native notification/CallKeep own it independently), matching normal phone behavior. Connected/outgoing-ringing calls still hang up on unmount as before.
